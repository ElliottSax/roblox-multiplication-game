# Ideas & Roadmap

_Generated by an autonomous brainstorm pass. Scored for feasibility and impact - "Ready to implement" items are small enough to ship as-is; "Future roadmap" items are good ideas that need a design decision, new assets, or more scope than a single pass should take on autonomously._

## Ready to implement next

### Comeback Buff for Lapsed Players
**Pitch:** The daily streak system rewards players who never miss a day but does nothing for someone who's been gone 3, 7, or 30 days. Using the same `LastPlayed` timestamp, detect an absence over a threshold (48h+) and grant a time-limited "Welcome Back" buff on rejoin (a currency multiplier or free rebirth-tier-equivalent boost for 20-30 minutes), scaled to how long they were gone. Targets win-back of players who already churned, a distinct lever from the login streak.

**Scope estimate:** ~100-150 LOC: a check in the `PlayerAdded` flow (`init.server.lua` / `DataService`) comparing now vs `LastPlayed`, a temporary multiplier flag consumed by `CurrencyService`, and a toast reusing the `RebirthAnnouncement`-style RemoteEvent pattern already in the codebase.

**Why it scored well:** `Stats.LastPlayed` is already tracked correctly — set on first-ever data creation and refreshed on every save/leave, so the value loaded on next join is a genuine "time since last session ended." The `PlayerAdded` flow already has `playerData` in scope for the threshold check to drop into directly. The RemoteEvent + client toast pattern is a proven copy-adapt from `RebirthService:AnnounceRebirth` and `RebirthUI:ShowMessage`, not hand-waving. The one gap — `CurrencyService` has no real "multiplier stack" to plug into, just two hardcoded local multipliers — is trivial new plumbing (a small session-scoped table with an expiry), not a blocker. No new assets, no owner design call beyond tuning the threshold/multiplier constants.

### Live Session Leaderboard + Spectate
**Pitch:** Add a small always-visible "Top Earners This Server" sidebar (session-only ranking, driven by lightweight RemoteEvent pushes rather than the slow all-time DataStore board) with a "Spectate" button that swaps the viewer's camera to that player's character — an aspirational, learn-by-watching loop the game doesn't have today.

**Scope estimate:** ~150-200 LOC realistically closer to 220-280 once edge cases are handled: new `SessionLeaderboardService` (ServerScriptService) plus a new `SessionLeaderboardUI.lua` (StarterGui). Reuses existing leaderstats/CurrencyService hooks; no new DataStores or assets.

**Why it scored well:** The exact scaffolding already exists — `CreateRemoteEvents()` in `init.server.lua` is the established place to add a push-style broadcast (mirrors `ComboUpdate`), and `CurrencyService` already exposes optional service hooks (`self.AchievementService`, `self.QuestService`, etc.) set once at init, so adding `self.SessionLeaderboardService` is the same pattern, not new architecture. There's exactly one shared server-wide path, so all players are mutually visible and spectating the leader watching real gate choices is meaningful. Spectate needs zero new remotes — characters already replicate to every client, so `CurrentCamera.CameraSubject` swap is pure client code. Docked slightly because it touches 3 existing files and a correct version needs respawn/leave/exit-spectate handling the naive estimate glosses over, but none of that needs a design decision.

### Floating Currency Gain Popups
**Pitch:** `GameUI.lua`'s `UpdateUI()` just swaps the "Currency: N" text with a blocking size-flash — a +5 and a +5000 collection feel identical. Add a small floating "+N" label that spawns near the currency icon, tweens upward and fades, color-scaled (green for small, gold for big gains), reusing the TweenService pattern already used in `ComboUI`/`AchievementUI`.

**Scope estimate:** ~40-90 LOC, single-file change to `src/StarterGui/GameUI.lua`; reuses the existing TweenService pattern and preloaded sounds, no new assets.

**Why it scored well:** The "no per-gain feedback exists today" premise is confirmed, and the TweenService pattern is a real, established idiom in this codebase (`ComboUI.lua`), not invented. Three real implementation gotchas were found and are all trivially fixable within the same file: `UpdateUI` fires on both `Currency` and `Collected` changes (needs a diff guard to avoid double-firing), `Currency.Value` also decreases on spending (needs a `delta > 0` guard), and the pitch's proposed client-side sound would audibly double the sound `CurrencyService:CollectObject` already plays server-side per pickup (fix: drop the redundant sound trigger, visual-only). None of this adds new scope or files. High player impact — Currency is the single most-watched number in this incremental loop and currently gets zero differentiated feedback.

### Gate-Hit Screen Flash
**Pitch:** `MultiplierService:PlayGateEffect` only flashes the gate part itself — there's no player-facing acknowledgment when a big x5/Power gate is triggered. Add a full-screen color-flash tinted with the gate's own configured color, fired to the nearest player, with intensity/duration scaled by gate value.

**Scope estimate:** ~50-70 LOC: one new RemoteEvent, a firing call in `MultiplierService.lua`, a listener+flash Frame in `GameUI.lua`. Reuses existing gate `Color` config and the TweenService flash pattern; no new assets.

**Why it scored well:** `OnObjectTouched` already computes `nearestPlayer` before calling `PlayGateEffect` — the exact hook point and player reference this needs already exist. `Config.Multipliers` already carries a `Color3` per gate entry. `RebirthUI`'s `ShowRebirthAnimation` is a verified working precedent for the exact full-screen-flash technique. `init.server.lua`'s `CreateRemoteEvents` and the existing `ComboUpdate:FireClient(nearestPlayer, ...)` call are direct, already-in-production precedents for "fire to nearest player." Two minor inaccuracies in the pitch ("Jackpot" is actually a sub-outcome of the Random gate, not its own type; `GateSound` isn't literally shared RemoteEvent plumbing) don't change the scope — both are one-line implementer judgment calls.

### Rebirth-Ready Idle Pulse
**Pitch:** The floating Rebirth button stays static even when `CanRebirth` becomes true — players only discover they can rebirth by opening the panel. Add a looping breathing glow on the button and play the already-defined-but-unused `SoundService.Sounds.RebirthReady` chime the moment it first becomes true.

**Scope estimate:** ~50-70 LOC in `src/StarterGui/RebirthUI.lua`; wires up an already-defined-but-unused sound ID, no new assets.

**Why it scored well:** Confirmed the floating button has zero visual state tied to `CanRebirth` today, and `RebirthReady` really is a defined sound that's genuinely never played anywhere in the codebase — a real dead-asset bug, not a generic suggestion. Two real gaps were found and are both fixable in the same file: `UpdateDisplay`'s poll currently only runs while the panel is open (needs loosening to detect the flip while idle), and the sound must be played via `ReplicatedStorage.GameSounds` (the client-reachable replicated copy) rather than the server-only `SoundService` module the pitch names literally. Neither requires new assets, remotes, or server changes. Genuine, on-tone fix for a real gap in the game's most important long-term-progression signal.

### Pet Card Hover + Equipped Idle Bob
**Pitch:** Pet inventory cards and equipped-slot icons in `PetUI.lua` are inert Frames — only the top-level pet button has a hover tween. Add a quick hover scale-up on each card (mirroring the existing button pattern) and a slow continuous bob + rarity-color glow pulse on the equipped-slot icons.

**Scope estimate:** ~50-70 LOC in `src/StarterGui/PetUI.lua` (`CreatePetCard` + `RefreshEquipped`); pure TweenService/UIStroke changes on existing frames, no new assets.

**Why it scored well:** `CreatePetCard`'s invisible hover button and `RefreshEquipped`'s plain inert `TextLabel` icon are both confirmed as described, and `RarityColors` is already in scope at the exact call site. `RefreshEquipped` destroys and rebuilds its slot children on every call, so newly created looped tweens die with their target automatically — no leak-guarding needed. Scored lower on player impact (3) because this is menu-chrome polish adjacent to, not inside, the core push-objects-through-gates loop.

### First-Minute Guided Onboarding Overlay
**Pitch:** A new player spawns to 7 independent floating UI buttons appearing simultaneously with zero explanation, plus a buried 2-line instructions label. Add a short guided sequence on first join — welcome banner, a waypoint toward the first gate, and a single highlighted call-to-action — so the first thing a new player does is understood and rewarding.

**Scope estimate:** ~150-250 LOC: mostly one new file (`OnboardingUI.lua`), plus minor persistence touches to `DataService.lua`. No new art/audio assets — reuses existing BillboardGui/particle patterns already in the codebase.

**Why it scored well:** The "wall of UI" problem is real and confirmed worse than described (6+ independently-positioned toggle buttons, no shared UI helper module). The sample CTA ("push the Goblin through the gate") is accurate to the actual fallback object type, not generic filler. Every technique the pitch proposes to reuse already has an in-repo precedent (ScreenGui/BillboardGui/ParticleEmitter patterns, the RemoteEvent factory, `DataService`'s additive default-data migration for a new persisted flag). Docked one point on feasibility only because true once-per-player persistence and the waypoint-arrow math (`WorldToScreenPoint` tracking, edge clamping) are real logic beyond a static label — a genuine multi-piece feature, though still no owner design decision required.

### Safe-Start Gate Curriculum
**Pitch:** Gates are picked via pure weighted-random from gate #1, so a brand-new player's first gate can be a Subtract or Divide before they've understood what a gate does. Guarantee the first few gates on the path are positive (Multiply/Add), with punishing/random types only appearing after that "safe zone."

**Scope estimate:** ~20-40 LOC: a small change to `MultiplierService:GenerateGatesOnPath`/`PickWeightedGate` plus one new `Config.lua` field for the safe-zone length. No new assets.

**Why it scored well:** Verified the single shared 6-gate path is generated with zero index-awareness today, genuinely mixing Subtract/Divide in from gate #1. The fix is pure data/control-flow — filtering the gate pool by type for the first N gates — with no new instances, assets, schema migration, or per-player state (the path is server-global). Fits the existing config-driven gate pattern exactly. Needs no owner design call beyond an obviously-reasonable default (2-3 of 6 gates).

### Concrete First-Session Goal Banner
**Pitch:** There's no stated objective after spawn. Add a small persistent goal banner stating one concrete near-term target on first join (e.g. progress toward the first Rebirth tier), swapping to the next milestone once hit.

**Scope estimate:** ~100 LOC, pure client-side — `GetRebirthInfo` (a RemoteFunction already exposed in `init.server.lua`) already returns exactly the shape needed (`NextTier.Required`, `.Current`, `.Progress`, `.Name`), so no new server plumbing is required at all, contrary to the original estimate.

**Why it scored well:** The onboarding gap is real — Rebirth progress is hidden inside a modal that only opens on click, and the corner HUD states no goal at all. One correction found: the pitch's example target ("reach 500 currency") actually matches `QuestService`'s daily-quest target, not `RebirthService`'s actual tier-1 threshold (10,000 currency) — a 20x gap that would show new players an unreachable first-session goal if implemented literally. This is a straightforward source fix within normal implementer judgment (pull the near-term goal from the daily quest, use the Rebirth tier as the session-spanning follow-up), not an owner-level design call.

## Future roadmap

### Welcome-Back Idle Payout
**Pitch:** Currency only accrues while actively playing — leave, and progress stops dead. Add a capped passive-earnings calc off `LastPlayed` and the player's recent earn rate: a claimable "while you were away" lump sum on rejoin, capped and scaled down so it never beats actually playing.

**Blocked on:** Scope was understated as reuse. There is no per-session earn-rate tracking anywhere — `DataService.Stats.PlayTime` is never incremented (`IncrementStat` has zero call sites), so "compute rate from last session" requires new instrumentation (join/leave snapshot + diff), not existing data. Also needs owner tuning decisions (rate formula, cap window, scale-down percentage) and an anti-abuse fix (claiming must reset the session marker, not just wait for the next periodic save).

### Daily Login Reward Track
**Pitch:** `QuestService` already tracks a daily streak, but it's invisible — it only quietly boosts quest reward %. Surface it as its own visible 7-day reward calendar (currency, a pet egg, a temporary gate-luck boost) that pops on first join each day.

**Blocked on:** Design decision — the "temporary gate-luck boost" reward doesn't exist as a mechanic anywhere in the codebase (`MultiplierService.PetService` is a hook that's declared but never read), so shipping it means designing a brand-new timed-bonus system from scratch. The pet-egg reward also needs a new free/bypass path added to `PetService:HatchEgg`, which currently always deducts currency. Comparable existing UI files run 500-900+ lines, so the "~200 LOC" estimate is optimistic. A currency-only version of the 7-day calendar (no egg, no gate-luck reward) would clear the implement-now bar on its own.

### Weekly Leaderboard Season
**Pitch:** The 4 existing leaderboards are permanent and cumulative, so new players can never crack the top 100 against months of accumulated play. Add a week-keyed "This Week's Top Earners" board that resets every Monday, with a claimable end-of-week reward for top finishers.

**Blocked on:** The board-rotation half (a week-keyed OrderedDataStore name) is small and nearly implement-now by itself. The bundled reward mailbox is the blocker: no claim/pending-reward infrastructure exists to reuse, the pet-egg reward again needs a free-grant path `PetService` doesn't have, and Roblox servers are ephemeral with no cron/MessagingService coordination in this codebase — determining "the week just ended, reward the top 100 exactly once" is a real distributed-systems problem, not a UI hookup. Needs an owner decision on reward tiers and claim-timing semantics before code is written. Recommend shipping the board rotation alone now and roadmapping the mailbox separately.

### Friends Leaderboard Tab
**Pitch:** Add a "Friends" filter to the leaderboard panel, showing just the viewer's Roblox friends ranked against each other.

**Blocked on:** Scope — the proposed approach (filter the already-fetched top-100/1000 cached results against the friends list) won't work for the common case, since a typical player's friends are very unlikely to be in the global top ranks. The approach that actually works (paginated `GetFriendsAsync()` + a `GetAsync()` DataStore call per friend) means 30-100+ synchronous DataStore reads per tab-open with real throttling risk, plus a new per-viewer cache dimension the existing 60s global cache doesn't support. Also needs a design call: does "Friends" filter whichever of the 4 existing stat tabs is selected, or is it one fixed stat? No empty-state UI is scoped for players with zero in-game friends either.

### Shared Runway Co-op Push Bonus
**Pitch:** When 2+ players are simultaneously in push range of the same object, award a stacking "Team Push" currency bonus, making playing shoulder-to-shoulder strictly better than grinding alone.

**Blocked on:** Design call — the pitch's core claim ("already tracked via each player's PushZone.Touched") is wrong: `Touched` is a one-shot velocity-apply event today with no `TouchEnded` wiring and no per-object set of nearby players. Building it reliably means new per-object state, cleanup across at least 4 different object-destroy code paths, and resolving an unaddressed exploit — a pure-proximity bonus is farmable by standing near an object without pushing it. Needs the owner to define what "simultaneous" means (a snapshot timing decision, since the push zone and the collection zone are spatially different points) and whether proximity-only farming is acceptable.

### Population-Scaled Boss Waves
**Pitch:** Boss wave strength is fixed regardless of server population. Scale boss value/spawn count with live player count, and add a real-time "server contribution" mini-leaderboard during the wave with a top-contributor callout at the end.

**Blocked on:** The player-count-scaling half is trivial and near implement-now on its own. The contribution leaderboard is the blocker: it needs a wave-lifecycle concept that doesn't exist today (per-wave boss-remaining counter, a "wave complete" signal), plus a new contribution-tracking hook into `CurrencyService:CollectObject` — a hot, shared function driving achievements/quests/currency for every object in the game, in a different file than the pitch scoped. Needs a real design decision on wave lifecycle (does it timeout, can waves overlap) before implementation. Recommend splitting: ship the scaling now, roadmap the contribution leaderboard once wave-completion design is settled.

### VIP Gamepass (permanent QoL bundle)
**Pitch:** A single one-time gamepass bundling a capped currency boost, larger pickup radius, a leaderboard/chat VIP tag, and a permanent glow aura — comfort/status only, no exclusive power.

**Blocked on:** External dependency — needs Elliott to create a real Gamepass ID in Roblox Studio/website first; there's zero MarketplaceService usage anywhere in the repo today. Also a fairness design call: "larger pickup radius" doesn't correspond to any existing mechanic (collection only happens at one fixed zone, credited to whoever's nearest) — building it as scoped would let paying players snipe currency credit from non-paying players near the same object. "VIP name tag in chat" needs entirely new chat-hook infrastructure that doesn't exist. The multiplier + aura + leaderboard-tag subset alone would ship cleanly once these are resolved.

### Cosmetic Skins Shop (gates, trails, runway themes)
**Pitch:** Purely visual purchases — recolored gate skins, particle trails on pushed objects, alternate runway themes. Zero effect on value/multipliers/spawn rates.

**Blocked on:** This would be the game's first real-money monetization surface (no MarketplaceService code exists at all), needing externally-created Gamepass/DeveloperProduct IDs. More fundamentally, a design decision is needed before any code: the path and gates are single shared server-wide instances, not per-player, so a server-side skin as scoped would reskin the world for every player on the server, not just the purchaser — killing the "show off your purchase" social value that drives this kind of sale, unless a genuinely different (client-only local render, or new per-player-object tagging) approach is chosen.

### Pet Convenience & Cosmetics Pack
**Pitch:** An "Auto-Hatch" toggle (same odds, pure time-saver), cosmetic pet accessories that don't touch stats, and a 4th pet equip slot as a bounded one-time purchase.

**Blocked on:** External dependency — needs from-scratch MarketplaceService integration and Elliott creating the gamepass listings. Also real scope beyond the estimate: the equipped-slots UI hardcodes exactly 3 slots in two places and needs rebuilding to render dynamically; cosmetics need new persisted per-pet fields the save data doesn't currently carry plus a new UI picker tab. Auto-hatch also needs an owner UX decision on rate-limiting so it doesn't spam the existing hatch-reveal animation/sound.

### Supporter Badge (leaderboard/chat flair)
**Pitch:** A cheap, purely vanity purchase adding a badge icon and colored name on the leaderboard and above the player's head — zero gameplay effect.

**Blocked on:** Scope was significantly understated. Two of the three sub-features need entirely new subsystems that don't exist anywhere in the codebase: an above-head nametag/BillboardGui system, and a chat-hook (TextChatService or legacy Chat) for flair — neither has any code to build on. `LeaderboardService`'s DataStore entries store only a numeric score with no field for a supporter flag, so showing the badge on other players' leaderboard rows needs a new per-user lookup joined against every displayed row. Also needs a real Developer Product/Gamepass ID created externally by Elliott. The underlying idea is sound and safe (family-friendly, zero gameplay effect) but needs real subsystem design work first.

### Staged Menu Unlocks Instead of All-at-Once
**Pitch:** All 5-6 menu buttons (Achievements, Leaderboard, Rebirth, Quests, Pets) render and are clickable the instant a player spawns, well before those systems are relevant. Gate each button's visibility behind a first relevant milestone.

**Blocked on:** Design call — 2 of the 5 proposed milestones don't hold up against the real code. Quests are assigned essentially instantly at join (`RefreshQuestsIfNeeded` runs synchronously during init), so gating the Quests button on "quest assigned" is a no-op with no real delay. Pets has no "egg drop" concept at all — eggs are a fixed catalog bought/hatched on demand, not something that drops. Leaderboard has no proposed milestone in the pitch at all. Rebirth and Achievements alone already have real, reusable thresholds to gate on. Someone needs to define real unlock conditions for Pets and Leaderboard before this is a clean ticket — the underlying UX idea (don't show 5 unexplained progression menus to a brand-new player) is sound and worth doing once that's settled.

## Considered and passed on

None this pass — every idea the brainstorm surfaced cleared the bar for either immediate implementation or the future roadmap; nothing was rejected outright.
